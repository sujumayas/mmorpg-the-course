Buffer longer, save less

Write-behind keeps changes in memory and flushes each dirty entry every T seconds. Database writes fall off a cliff in the first few multiples of 1/u, then flatten. Crash loss keeps climbing in a straight line. Past the knee, a longer buffer buys almost nothing.

—write-through, N × u (writes/s)
—write-behind W(T) (writes/s)
—cut, 1 − W / N u
—writes saved per second of extra expected loss
—expected loss per crash, T/2
—worst case, T
—changes lost per entry, u T / 2
—knee, 1/u to 3/u

Model from DB201 week 8, section 2: each entry changes as a Poisson process at rate u, and a flush writes an entry only if it changed since the last flush, so each entry is written with probability 1 − e−uT every T seconds. The presets use the lecture's figures: Redis appendfsync everysec flushes once a second; PostgreSQL with synchronous_commit = off can lose up to 3 × wal_writer_delay (200 ms by default); Minecraft autosaves every 5 minutes.
